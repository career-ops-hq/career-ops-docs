## Pi
Pi needs no wrapper file. It reads `AGENTS.md` from the career-ops folder and finds the shared skill on its own, so you start `pi` in that folder and call career-ops with `/skill:career-ops`, followed by the mode you want. For a single unattended run, use `pi -p "your prompt"`.
Some Pi builds ask you to trust a project before they load its skills. If `/skill:career-ops` is not available, run `/trust` once in the folder and then restart `pi`: the trust decision only applies to Pi sessions started afterwards. To install Pi, follow [Pi's own instructions](https://github.com/earendil-works/pi).

**Yes — career-ops runs first-class on Windows.** There is one Windows-specific caveat, and the installer handles it for you automatically: no Developer Mode, no manual `mklink`, and no minimum-OS requirement. If you have Node installed, you install and run career-ops on Windows exactly like anywhere else.
## The one Windows caveat, handled for you
Windows does not create symlinks by default, so a fresh Git checkout leaves the CLI skill entrypoints (`.claude/skills/`, `.opencode/skills/`, and so on) as plain pointer files instead of real symlinks — which is what causes the "skills aren't loading" error people hit on other tools.
career-ops detects this automatically. Running the installer or updater — `npx @santifer/career-ops init` on a fresh install, or `node update-system.mjs apply --confirm` on an update — runs a `materializeSkillEntrypoints` step that replaces those pointer files with the full skill content. From a linked Git worktree, `node update-system.mjs apply --confirm` makes this repair in your `main` checkout. Run `git merge main` in the worktree to pick it up; worktrees created from the updated `main` already have it. With `CAREER_OPS_UPDATE_IN_WORKTREE=1` set, `apply` repairs only that worktree's branch instead, and `main` stays unrepaired. You do not need admin rights, Developer Mode, or any manual `mklink` command.
<Callout title="No minimum-OS requirement">
career-ops does not require any particular Windows (or macOS) version. If Node runs, career-ops runs. Any claim of a minimum OS version you may have seen elsewhere is not accurate.
</Callout>

Every term career-ops uses, defined in one place. Terms link to the deeper reference where one exists.
## ATS (Applicant Tracking System)
The software companies use to receive, store, and filter job applications — [Greenhouse](/docs/reference/portals/greenhouse), [Ashby](/docs/reference/portals/ashby), and [Lever](/docs/reference/portals/lever) are common examples. career-ops reads their public job APIs to discover openings and can pre-fill their application forms, but never auto-submits.
## Global score (1-5)
The LLM's holistic judgement of a job listing across five dimensions (match, north-star alignment, comp, cultural signals, red flags), producing a score from 1 to 5. At 4.5+ the agent recommends applying immediately; below 4.0 it recommends against applying. There is no closed-form weighting formula: the score is the LLM's judgement given the rubric, which is public on the [methodology page](https://career-ops.org/methodology).
## Data Contract
career-ops's core architectural promise: the **system layer** (scripts, modes, templates) is updatable at any time, while the **user layer** — `cv.md`, `config/profile.yml`, `data/`, `reports/`, `output/` — is never touched by an update. Your data outlives every version.
## Spray-and-pray
The mass-application strategy of sending the same CV to hundreds of jobs with no targeting. career-ops explicitly rejects it: the pipeline evaluates and ranks listings first, so effort concentrates on the small set of roles worth pursuing.
## Liveness check
A heuristic career-ops runs to detect whether a job listing is still open before you spend time or tokens on it. It is a best-effort signal — expired postings sometimes linger on job boards — and listings can be marked manually when the heuristic is wrong.
## Tailoring
Rewriting your CV for one specific job listing — reordering emphasis, surfacing matching skills and metrics, aligning vocabulary with the job description — while keeping every claim truthful to your real experience. career-ops generates a tailored CV per application as Markdown you can edit.
## Mode
A focused, prompt-defined workflow that career-ops ships as a plain Markdown file your AI CLI executes — [scan, apply, tracker](/docs/reference/modes), [interview/practice](/docs/introduction/guides/interview-modes), and a dozen more. Modes are inspectable text, not black-box code.
## Pipeline
The end-to-end career-ops workflow: scan portals → evaluate listings (1-5) → tailor CV → apply → track → prepare interviews. Each stage is a mode you can run independently or as a batch.
## Zero-token scan
A discovery run that consumes no LLM tokens: `scan.mjs` reads ATS APIs, job-board feeds and career pages directly over HTTP, so finding new listings is free regardless of which AI engine you use.
## AI engine
The AI coding CLI that executes career-ops prompts — Claude Code, OpenCode, Codex, GitHub Copilot CLI, and [other supported CLIs](/docs/supported-clis) — or any OpenAI-compatible endpoint. career-ops is engine-agnostic and [runs on free engines too](/docs/free-ai-engine).
## Question bank
A local Markdown file (`interview-prep/question-bank.md`) where career-ops accumulates real interview questions and your performance on each (✅/🟡/🔴). The [interview/debrief mode](/docs/introduction/guides/interview-modes) updates it after every real interview, so preparation compounds across rounds.
## STAR+R story
An interview story structured as **S**ituation, **T**ask, **A**ction, **R**esult, plus **R**eflection — the format career-ops uses in its story bank so behavioral answers are concrete, quantified, and reusable across interviews.
## Story bank
A local Markdown file (`interview-prep/story-bank.md`) of your prepared STAR+R stories. Practice sessions verify answers against it, and debriefs extract new stories from what you actually said in real interviews.
## Portal
A company career site backed by an ATS that career-ops can scan. Your tracked portals live in `portals.yml`; the scanner reads their public APIs on every run.
## Batch evaluate
Scoring many saved listings in one run instead of one at a time, with flags to keep control: `--limit` caps the batch size, `--dry-run` previews what would be processed, and `--resume-paused` continues an interrupted run without re-spending tokens. A `needs_confirmation` job is an artifact-free hold that only the parent interactive session resumes after an explicit answer; retry and paused-resume flags leave it held.
## Local-first
The career-ops architecture principle: everything — your data, the prompts, the scripts, the AI CLI — runs on your machine. There is no hosted backend, no account, and nothing to sign up for.
## CareerOps
CareerOps is the practice of running a job search the way engineers run production: with evidence, with discipline, and with tools on the candidate's side of the table. The term names the practice, not a product; career-ops is its first reference implementation. Coined by Santiago Fernández de Valderrama Aparicio in [The CareerOps Manifesto](https://career-ops.org/manifesto) (July 14, 2026).

## ATS (Applicant Tracking System)
Il software che le aziende usano per ricevere, archiviare e filtrare le candidature: [Greenhouse](/it/docs/reference/portals/greenhouse), [Ashby](/it/docs/reference/portals/ashby) e [Lever](/it/docs/reference/portals/lever) sono tra gli esempi più diffusi. career-ops legge le loro API pubbliche per scoprire le posizioni aperte e può precompilare i loro moduli di candidatura, ma non invia mai: sei tu a cliccare su Invia.
## Punteggio globale (da 1 a 5)
Il giudizio complessivo dell'LLM su un annuncio di lavoro, basato su cinque dimensioni (corrispondenza con il profilo, allineamento con la tua north star, retribuzione, segnali culturali, red flag), che produce un punteggio da 1 a 5. Da 4,5 in su l'agente consiglia di candidarsi subito; sotto 4,0 lo sconsiglia. Non esiste una formula chiusa di ponderazione: il punteggio è il giudizio dell'LLM alla luce della griglia di valutazione, che è pubblica nella [pagina sulla metodologia](https://career-ops.org/methodology).
## Data Contract
La promessa architetturale alla base di career-ops: il **livello di sistema** (script, modalità, template) si può aggiornare in qualsiasi momento, mentre il **livello utente** — `cv.md`, `config/profile.yml`, `data/`, `reports/`, `output/` — non viene mai toccato da un aggiornamento. I tuoi dati sopravvivono a ogni versione.
## Spray-and-pray
La strategia delle candidature di massa: inviare lo stesso curriculum a centinaia di annunci, senza alcuna selezione. career-ops la rifiuta esplicitamente: la pipeline prima valuta e ordina gli annunci, così l'impegno si concentra sul piccolo gruppo di ruoli per cui vale davvero la pena candidarsi.
## Liveness check
Un'euristica con cui career-ops verifica se un annuncio è ancora aperto prima che tu ci spenda tempo o token. È un segnale indicativo, non una garanzia — gli annunci scaduti a volte restano online sui siti di ricerca lavoro — e puoi contrassegnare un annuncio a mano quando l'euristica sbaglia.
## Tailoring (adattare il curriculum all'annuncio)
Riscrivere il tuo curriculum per un annuncio specifico — riordinando le priorità, mettendo in evidenza le competenze e i numeri pertinenti, allineando il vocabolario a quello della descrizione del ruolo — senza che nessuna affermazione si allontani dalla tua esperienza reale. career-ops genera un CV su misura per ogni candidatura, in Markdown che puoi modificare.
## Modalità
Un flusso di lavoro mirato, definito da un prompt, che career-ops distribuisce come semplice file Markdown eseguito dalla tua CLI AI: [scan, apply, tracker](/it/docs/reference/modes), [interview/practice](/it/docs/introduction/guides/interview-modes) e una dozzina di altre. Le modalità sono testo che puoi ispezionare, non codice a scatola chiusa.
## Pipeline
Il flusso di lavoro completo di career-ops: scansione dei portali → valutazione degli annunci (da 1 a 5) → curriculum su misura → candidatura → monitoraggio → preparazione dei colloqui. Ogni fase è una modalità che puoi eseguire da sola oppure in batch.
## Scan a zero token
Una ricerca di nuovi annunci che non consuma token LLM: `scan.mjs` legge le API degli ATS, i feed dei siti di annunci e le pagine "Lavora con noi" direttamente via HTTP, quindi trovare nuovi annunci è gratuito qualunque motore AI tu usi.
## Motore AI
La CLI AI per la programmazione che esegue i prompt di career-ops — Claude Code, OpenCode, Codex, GitHub Copilot CLI e [le altre CLI supportate](/it/docs/supported-clis) — oppure qualsiasi endpoint compatibile con OpenAI. career-ops non dipende da un motore specifico e [funziona anche con motori gratuiti](/it/docs/free-ai-engine).
## Question bank (archivio delle domande)
Un file Markdown locale (`interview-prep/question-bank.md`) in cui career-ops raccoglie le domande reali dei colloqui di lavoro e come te la sei cavata con ciascuna (✅/🟡/🔴). La [modalità interview/debrief](/it/docs/introduction/guides/interview-modes) lo aggiorna dopo ogni colloquio reale, così la preparazione si accumula da un colloquio all'altro.
## Storia STAR+R
Una storia da colloquio strutturata in **S**ituation (situazione), **T**ask (compito), **A**ction (azione), **R**esult (risultato), più **R**eflection (riflessione): è il metodo STAR con un passaggio in più, e il formato che career-ops usa nel suo story bank perché le risposte comportamentali siano concrete, quantificate e riutilizzabili in più colloqui.
## Story bank (archivio delle storie)
Un file Markdown locale (`interview-prep/story-bank.md`) con le tue storie STAR+R già preparate. Le sessioni di pratica confrontano le tue risposte con questo archivio, e i debrief ne ricavano nuove storie da ciò che hai detto davvero nei colloqui reali.
## Portale
Il sito "Lavora con noi" di un'azienda, basato su un ATS, che career-ops è in grado di scansionare. I portali che segui sono elencati in `portals.yml`; a ogni esecuzione lo scanner legge le loro API pubbliche.
## Valutazione in batch
Assegnare un punteggio a molti annunci salvati in un'unica esecuzione, invece che uno alla volta, con opzioni per non perdere il controllo: `--limit` fissa la dimensione massima del batch, `--dry-run` mostra in anteprima che cosa verrebbe elaborato e `--resume-paused` riprende un'esecuzione interrotta senza spendere di nuovo token. Un job `needs_confirmation` è una sospensione che non produce artefatti e che solo la sessione interattiva principale riprende dopo una risposta esplicita; le opzioni di nuovo tentativo e di ripresa dei job in pausa lo lasciano sospeso.
## Local-first
Il principio architetturale di career-ops: tutto — i tuoi dati, i prompt, gli script, la CLI AI — gira sulla tua macchina. Non c'è un backend ospitato, non c'è un account e non c'è niente a cui iscriversi.
## CareerOps
CareerOps è la pratica di cercare lavoro come gli ingegneri gestiscono la produzione: con prove, con disciplina e con strumenti dalla parte del candidato. Il termine indica la pratica, non un prodotto; career-ops ne è la prima implementazione di riferimento. Coniato da Santiago Fernández de Valderrama Aparicio in [The CareerOps Manifesto](https://career-ops.org/manifesto) (14 luglio 2026).

The scanner reads your enabled Greenhouse slugs from portals.yml, calls the public boards API for each one, and adds new, title-matching roles to your pipeline with no scraping and zero LLM tokens spent on the fetch. node scan.mjs

## How career-ops talks to Greenhouse
career-ops requests `boards-api.greenhouse.io/v1/boards/{slug}/jobs` and reads the `jobs` array from the JSON, taking each role's title and its `absolute_url`. That boards endpoint returns listing metadata — title, location, and department — but not the full description, so career-ops pulls the complete job text with a follow-up request per role during the evaluate step, or by appending `?content=true` where the board supports it. ## Gotchas
Greenhouse-API listings only include the title, location, and department in the boards endpoint. Full JD text requires a follow-up request per listing, which career-ops handles automatically during the evaluate step.

## How career-ops talks to Ashby

---
title: Prepare for Interviews
description: Use the interview modes — plan, practice, debrief — to prepare for a specific interview round, rehearse it with an AI interviewer, and turn every real interview into intelligence for the next one.
seoTitle: "Interview prep with career-ops — round-by-round preparation"
icon: GraduationCap
---
The interview modes are career-ops's interview preparation system, shipped in v1.16.0: `interview/plan` builds a time-blocked prep plan for a specific round, `interview/practice` runs a text mock interview one question at a time, and `interview/debrief` captures what actually happened so the next round starts smarter. Together they form a loop — plan, practice, interview, debrief, repeat — that compounds across a hiring process.
They complement the older [`interview-prep` mode](/docs/reference/modes/interview-prep), which builds your durable foundation (story bank, question bank). The three focused modes are about a *specific upcoming round*.
<Callout title="What you need first">
A workspace with your `cv.md` and `config/profile.yml` in place (the [Quick Start](/docs) sets both up). The modes read them to ground every plan and every piece of feedback in your real experience — not generic interview advice.
</Callout>
## The loop at a glance
| Mode | When | What you get |
| --- | --- | --- |
| `interview/plan` | The moment a round is scheduled | A time-blocked prep plan sized to the hours you actually have |
| `interview/practice` | Before the round | A text mock interview with structured feedback per answer |
| `interview/debrief` | Right after the real interview | An honest per-question assessment + an updated question bank |
## Plan: turn a date into a schedule
Give `interview/plan` the job description and the interview date and time, plus the round type and interviewer if you know them. It reads your CV and profile, runs an honest fit assessment — strengths to anchor on, gaps likely to be tested — and divides the hours you have left into concrete prep blocks.
```txt title="Example"
/career-ops interview/plan
→ Inputs: JD (pasted), interview Thursday 14:00, HM screen with Ana (Eng Manager)
→ Fit assessment: 4 strengths to anchor · 2 gaps ranked by test likelihood
→ Plan (9 hours available):
   Block 1 — Lock your narrative (~1.5h): timeline, "why us", strongest proof point
   Block 2 — Gap: event-driven architectures (~3h)
   Block 3 — Behavioral stories, STAR+R (~2h)
   Block 4 — Mock run + comp answer (~1.5h)
```
The plan calibrates to the round: a recruiter screen gets logistics and narrative, not deep internals; a practitioner deep-dive gets depth in the core skill from the JD. If a question bank from a previous round exists, anything you struggled with gets a dedicated block — real performance data outranks inferred risk.
## Practice: rehearse one question at a time [#practice-rehearse-against-a-realistic-interviewer]
`interview/practice` plays the interviewer — by name and role if you provide them — and asks one question at a time, staying in character, with natural follow-ups when a real interviewer would push deeper. After each answer you get structured feedback: what landed, what to tighten, and a stronger version of your answer grounded in your actual CV and story bank.
It also tracks the session the way an interviewer would: if you reach for the same story twice, it flags that your example set reads thin; if your answer closes on the wrong domain for the role, it tells you where to land it instead.
<Callout>
Practice is honest about its own limits: if you haven't built a question bank or role-specific prep notes yet, it says so and offers to run `interview-prep` or `interview/plan` first, rather than silently running a generic session.
</Callout>
## Debrief: never lose an interview's intelligence
Run `interview/debrief` right after a real interview, while memory is fresh. It walks you through every question you can recall, records how the interviewer reacted, and produces an honest per-question assessment. Then it does the compounding work:
- **Updates the question bank** — each question marked ✅ / 🟡 / 🔴 based on real performance, not gut feeling.
- **Closes the gaps** — for every 🔴, it explains the correct answer with a worked example and connects it to a story you already have.
- **Extracts new stories** — if you told something in the room that isn't in your story bank yet, it offers to build it into a STAR+R story and adds it if you say yes.
- **Predicts the next round** — if you know the format, it lists likely questions, each labeled `[inferred]`, from the interviewer's role and what this round already covered.
## Why this loop works
Interview prep usually resets to zero with every round. The interview modes make it cumulative: what a real interviewer actually asked becomes the highest-priority prep signal for the next round, stored in plain Markdown files (`interview-prep/question-bank.md`, `story-bank.md`) that you own, on your machine, like everything else in career-ops.

Le modalità di colloquio sono il sistema di preparazione ai colloqui di career-ops, disponibile dalla v1.16.0: `interview/plan` costruisce un piano di preparazione a blocchi orari per una fase specifica, `interview/practice` conduce una simulazione di colloquio testuale, una domanda alla volta, e `interview/debrief` registra ciò che è successo davvero, così la fase successiva parte da una base migliore. Insieme formano un ciclo (piano, pratica, colloquio, debriefing, e di nuovo da capo) i cui benefici si sommano lungo tutto il processo di selezione.
Completano la più vecchia [modalità `interview-prep`](/it/docs/reference/modes/interview-prep), che costruisce le tue fondamenta durature (archivio di storie, archivio di domande). Le tre modalità mirate riguardano invece una *specifica fase in arrivo*.
<Callout title="Cosa ti serve prima">
Uno spazio di lavoro con `cv.md` e `config/profile.yml` già al loro posto (la [Guida rapida](/it/docs) li configura entrambi). Le modalità li leggono per ancorare ogni piano e ogni feedback alla tua esperienza reale, non a consigli generici sui colloqui.
</Callout>
## Il ciclo in breve
| Modalità | Quando | Cosa ottieni |
| --- | --- | --- |
| `interview/plan` | Appena viene fissata una fase | Un piano di preparazione a blocchi orari, dimensionato sulle ore che hai davvero |
| `interview/practice` | Prima della fase | Una simulazione di colloquio testuale con feedback strutturato per ogni risposta |
| `interview/debrief` | Subito dopo il colloquio reale | Una valutazione onesta domanda per domanda + un archivio di domande aggiornato |
## Piano: come organizzare la preparazione a partire dalla data del colloquio
Dai a `interview/plan` la descrizione della posizione, la data e l'ora del colloquio, più il tipo di fase e il nome dell'intervistatore, se li conosci. Legge il tuo curriculum e il tuo profilo, esegue una valutazione onesta della compatibilità (i punti di forza su cui fare leva, le lacune che con ogni probabilità verranno messe alla prova) e divide le ore che ti restano in blocchi di preparazione concreti.
```txt title="Esempio"
/career-ops interview/plan
→ Inputs: JD (pasted), interview Thursday 14:00, HM screen with Ana (Eng Manager)
→ Fit assessment: 4 strengths to anchor · 2 gaps ranked by test likelihood
→ Plan (9 hours available):
   Block 1 — Lock your narrative (~1.5h): timeline, "why us", strongest proof point
   Block 2 — Gap: event-driven architectures (~3h)
   Block 3 — Behavioral stories, STAR+R (~2h)
   Block 4 — Mock run + comp answer (~1.5h)
```
Il piano si calibra sulla fase: per un primo colloquio con il recruiter prevede logistica e narrazione, non i dettagli tecnici più profondi; per un approfondimento tecnico con chi fa quel lavoro prevede profondità nella competenza chiave indicata nell'annuncio. Se esiste un archivio di domande di una fase precedente, tutto ciò che ti ha messo in difficoltà riceve un blocco dedicato: i dati reali sulle tue prestazioni contano più del rischio ipotizzato.
## Pratica: come simulare un colloquio una domanda alla volta [#practice-rehearse-against-a-realistic-interviewer]
`interview/practice` interpreta l'intervistatore, con nome e ruolo se li fornisci, e fa una domanda alla volta, restando nel personaggio, con domande di approfondimento naturali là dove un vero intervistatore andrebbe più a fondo. Dopo ogni risposta ricevi un feedback strutturato: cosa ha funzionato, cosa rendere più incisivo e una versione più forte della tua risposta, basata sul tuo curriculum reale e sul tuo archivio di storie.
Tiene anche traccia della sessione come farebbe un intervistatore: se ricorri due volte alla stessa storia, ti segnala che il tuo repertorio di esempi appare scarno; se la tua risposta si chiude sull'ambito sbagliato per il ruolo, ti dice dove farla approdare.
<Callout>
La pratica è onesta sui propri limiti: se non hai ancora costruito un archivio di domande o degli appunti di preparazione specifici per il ruolo, lo dice e ti propone di eseguire prima `interview-prep` o `interview/plan`, invece di avviare in silenzio una sessione generica.
</Callout>
## Debriefing: cosa fare dopo un colloquio per non perdere ciò che hai imparato
Esegui `interview/debrief` subito dopo un colloquio reale, finché il ricordo è fresco. Ti accompagna attraverso ogni domanda che riesci a ricordare, registra come ha reagito l'intervistatore e produce una valutazione onesta domanda per domanda. Poi fa il lavoro che si accumula nel tempo:
- **Aggiorna l'archivio di domande**: ogni domanda viene contrassegnata con ✅ / 🟡 / 🔴 in base alla prestazione reale, non alle sensazioni.
- **Colma le lacune**: per ogni 🔴 spiega la risposta corretta con un esempio svolto e la collega a una storia che hai già.
- **Estrae nuove storie**: se durante il colloquio hai raccontato qualcosa che non è ancora nel tuo archivio di storie, ti propone di trasformarlo in una storia STAR+R e lo aggiunge se dici di sì.
- **Prevede la fase successiva**: se conosci il formato, elenca le domande probabili, ciascuna etichettata `[inferred]`, a partire dal ruolo dell'intervistatore e da ciò che questa fase ha già coperto.
## Perché questo ciclo funziona
Di solito la preparazione ai colloqui riparte da zero a ogni fase. Le modalità di colloquio la rendono cumulativa: ciò che un vero intervistatore ha chiesto davvero diventa il segnale di preparazione con la priorità più alta per la fase successiva, conservato in semplici file Markdown (`interview-prep/question-bank.md`, `story-bank.md`) che sono tuoi, sul tuo computer, come tutto il resto in career-ops.
