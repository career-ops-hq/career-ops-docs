Usa esta guía cuando tengas 10 o más ofertas de empleo que revisar y quieras procesarlas todas en una sola sesión en lugar de una a una.

Cada oferta recibe su propio worker, una sesión headless de Claude Code salvo que [elijas otro CLI](#run-the-batch-on-another-cli). Ese worker lee tu CV, puntúa el encaje, redacta un informe completo y guarda un PDF adaptado — todo sin que muevas un dedo.

## Paso 1: Añade tus ofertas al archivo de entrada

El sistema de batch lee las URLs de las ofertas desde un archivo llamado **`batch/batch-input.tsv`**. Piensa en él como una lista de tareas para el evaluador.

<div className="rounded-lg bg-radial-[at_bottom] from-blue-500/20 p-4 border bg-origin-border border-fd-primary/10 prose-no-margin dark:bg-black/20">
  <div className="rounded-xl bg-fd-background p-3">
    <Steps>
      <Step>
        Abre **`batch/batch-input.tsv`** en cualquier editor de texto.
      </Step>
      <Step>
        Añade una fila por oferta. Cada fila tiene cuatro columnas separadas por un tabulador:

        | Columna | Qué escribir |
        |--------|---------------|
        | `id` | Un número único para esta oferta (1, 2, 3, …) |
        | `url` | La URL completa de la oferta de empleo |
        | `source` | Dónde la encontraste (p. ej., `LinkedIn`, `Greenhouse`) |
        | `notes` | Una nota opcional — déjala en blanco si no tienes ninguna |
      </Step>
      <Step>
        Guarda el archivo.
      </Step>
    </Steps>
  </div>
</div>

**Ejemplo:**

```text title="batch-input.tsv"
id	url	source	notes
1	https://jobs.example.com/senior-engineer	LinkedIn	
2	https://greenhouse.io/jobs/fullstack-dev	Greenhouse	priority
3	https://builtinaustin.com/job/rails-dev	BuiltIn	
```

<Callout title="Consejo">
  Cada ID debe ser un número único. No te saltes números ni los repitas.
</Callout>

## Paso 2: Previsualiza tu batch (recomendado)

Antes de procesar nada, ejecuta una comprobación rápida para ver cuántas ofertas están en espera. Todavía no se evalúa nada — esto es solo una vista previa.

```bash title="Terminal"
./batch/batch-runner.sh --dry-run
```

Verás una lista de las ofertas pendientes con sus IDs. Si algo no cuadra, corrige el archivo de entrada ahora, antes de dedicar tiempo a una lista incorrecta.

## Paso 3: Ejecuta el batch

Cuando estés listo, arranca el batch. Con workers de Claude Code, la opción por defecto, el runner evalúa tres ofertas a la vez; `--parallel` cambia ese número.

**De tres en tres (por defecto; más rápido, pero más exigente con tu máquina):**

```bash title="Terminal"
./batch/batch-runner.sh
```

**De dos en dos:**

```bash title="Terminal"
./batch/batch-runner.sh --parallel 2
```

**De una en una (la opción más lenta, la que menos memoria consume):**

```bash title="Terminal"
./batch/batch-runner.sh --parallel 1
```

**Omite las ofertas que puntúen por debajo de un umbral (p. ej., por debajo de 4.0 sobre 5):**

```bash title="Terminal"
./batch/batch-runner.sh --parallel 2 --min-score 4.0
```

Observa la terminal mientras corre el batch. Cada línea te indica qué oferta se está procesando y si terminó o falló.

Cuando un worker de Claude choca con un rate limit, el runner espera y vuelve a intentar la misma oferta dentro de la misma ejecución, sin esperar más de `--rate-limit-sleep` segundos (300 por defecto), y procesa el resto del batch con un solo worker. Cada uno de estos reintentos dentro de la ejecución consume uno de los intentos de `--max-retries` de la oferta. Un límite de sesión o de uso, en cambio, pausa el batch, y las ofertas que aún no había empezado quedan pendientes. Para terminar el batch más tarde, ejecuta `./batch/batch-runner.sh --resume-paused` para las ofertas pausadas y un `./batch/batch-runner.sh` sin opciones para las pendientes: cada comando omite las ofertas del otro.

### Ejecuta el batch con otro CLI [#run-the-batch-on-another-cli]

El runner usa Claude Code salvo que pases `--cli`. Acepta cinco valores: `claude` (por defecto), `opencode`, `gemini`, `qwen` y `grok`. `--model` elige el modelo de ese CLI:

```bash title="Terminal"
./batch/batch-runner.sh --cli opencode --model qwen2.5:32b
```

Los workers en paralelo y los reintentos por rate limit dentro de la ejecución son exclusivos de Claude. Con cualquier otro `--cli`, el runner evalúa una oferta a la vez (restablece `--parallel` a 1 con un aviso) y hace un solo intento por oferta en cada ejecución. Si ese intento falla, la oferta queda marcada como fallida y espera a una ejecución posterior, que la reintenta como se explica en el Paso 5. Consulta [CLIs de IA compatibles](/es/docs/supported-clis#which-clis-can-run-a-batch) para ver en qué se diferencia esta lista de los CLIs que career-ops soporta.

Si un worker delegado encuentra una oferta de agencia que requiere tu confirmación, se detiene antes de escribir un informe, CV, borrador de solicitud o fila del tracker y marca el trabajo como `needs_confirmation`. Responde a la pregunta mostrada en la sesión interactiva principal; esa sesión solo reanuda el trabajo retenido después de tu respuesta explícita. `--retry-failed` y `--resume-paused` no reanudan las retenciones por confirmación.

## Paso 4: Lee los resultados según van llegando

No necesitas esperar a que el batch termine. Los resultados aparecen a medida que se completa cada oferta.

**Informes de evaluación completos** → `reports/`

Cada informe es un archivo con un nombre del tipo `042-company-name-2026-04-14.md`. Ábrelo para ver:

- Un resumen del puesto
- Cómo de bien encaja tu CV con la oferta
- Un análisis salarial
- Un plan sugerido de preparación de la entrevista

Cada informe incluye también un **Risk Summary** (resumen de riesgos). Su fila **Fixed-term contract** (contrato de duración determinada) cita la formulación explícita de la oferta, muestra `✅ no fixed term disclosed` cuando no aparece ninguna y queda marcada como no evaluada cuando la descripción del puesto no estaba disponible. El campo correspondiente del Machine Summary es `risk_summary.fixed_term`, con uno de estos valores exactos:

| Valor | Significado |
|-------|-------------|
| `detected` | La oferta describe explícitamente un puesto de duración determinada |
| `not_detected` | No se encontró ninguna formulación explícita de duración determinada |
| `not_evaluated` | La descripción del puesto no estaba disponible para esta comprobación |

**Entradas para el tracker** → `batch/tracker-additions/`

Cada oferta deja también aquí un archivo con un resumen breve: una fila de encabezado con los nombres de las columnas y una fila de valores. Estos se añaden a tu tracker principal en el Paso 6.

### Score Evidence

El informe incluye **Score Evidence** después de Risk Summary. Abarca cinco dimensiones: ajuste del CV, alineación con North Star, remuneración, señales culturales y señales de alerta. Cada fila recoge un estado de evidencia (`supported`, `partial` o `unknown`), una fuente u observación concreta y una pregunta pendiente. La sección termina con un nivel de confianza en la evidencia (`High`, `Medium` o `Low`), su motivo y hasta tres prioridades de verificación.

Este nivel describe la evidencia que respalda el Global Score; no es una probabilidad de contratación ni el nivel de legitimidad del anuncio del bloque G, y no modifica la puntuación numérica. Machine Summary conserva los cinco estados en `score_evidence`, el nivel en `confidence` y las prioridades en `confidence_gaps`. Cuando no quedan prioridades, `confidence_gaps` es una lista vacía.

## Paso 5: Reintenta las ofertas fallidas

A veces un worker falla — por ejemplo, si la URL de una oferta dejó de cargar. Las ofertas fallidas aparecen en la terminal con un mensaje de error breve.

Estos son reintentos en ejecuciones posteriores y funcionan igual con cualquier CLI: la siguiente ejecución vuelve a tomar cada oferta fallida hasta que la oferta agota sus intentos de `--max-retries`. Son distintos de los reintentos por rate limit dentro de la ejecución del Paso 3, que solo hacen los workers de Claude, aunque ambos cuentan contra el mismo límite de `--max-retries`. Un `./batch/batch-runner.sh` sin opciones reintenta las ofertas fallidas junto con las pendientes.

**Reintenta solo las ofertas fallidas:**

```bash title="Terminal"
./batch/batch-runner.sh --retry-failed
```

**Reintenta con hasta 3 intentos en lugar de los 2 por defecto:**

```bash title="Terminal"
./batch/batch-runner.sh --retry-failed --max-retries 3
```

El batch omite cualquier oferta que ya terminó con éxito — así que volver a ejecutarlo es siempre seguro.

## Paso 6: Fusiona los resultados en tu tracker

Cuando el batch termine, ejecuta este comando para añadir todas las evaluaciones nuevas a `data/applications.md`:

```bash title="Terminal"
node merge-tracker.mjs
```

Este script:

1. Lee los archivos de resumen de `batch/tracker-additions/`
2. Comprueba duplicados para que nunca acabes con dos filas para la misma oferta
3. Añade las entradas nuevas a tu tracker de candidaturas
4. Archiva los archivos procesados en `batch/tracker-additions/merged/`

**Para previsualizar los cambios sin escribir nada:**

```bash title="Terminal"
node merge-tracker.mjs --dry-run
```

## Qué hacer a continuación

Abre **`data/applications.md`** para ver todas tus evaluaciones en una sola tabla. Desde ahí puedes:

- Ordenar por puntuación para encontrar tus mejores encajes
- Abrir los informes individuales en `reports/` para un análisis en profundidad
- Iniciar el proceso de candidatura para tus mejores opciones con `/career-ops apply`
